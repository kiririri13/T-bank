# Техническое задание

## 1. Общие сведения

**Наименование проекта:** T-Банк Loyalty Hub.

**Тип системы:** веб-приложение с backend API, статическим frontend, PWA-подготовкой и CI/CD.

**Назначение:** предоставить пользователю единый раздел лояльности Т-Банка на основе данных CSV-датасета: счета, программы лояльности, начисления, партнерские предложения, достижения, прогноз выгоды и рекомендации продуктов экосистемы.

**Репозиторий:** [https://github.com/kiririri13/T-bank](https://github.com/kiririri13/T-bank)

**Промышленный frontend:** [https://tbank-loyalty-hub.pages.dev/](https://tbank-loyalty-hub.pages.dev/)

**Промышленный backend/API:** [https://tbank-loyalty-hub-api.onrender.com](https://tbank-loyalty-hub-api.onrender.com)

**Health check:** [https://tbank-loyalty-hub-api.onrender.com/api/health](https://tbank-loyalty-hub-api.onrender.com/api/health)

## 2. Цели проекта

1. Создать демонстрационный личный кабинет лояльности для клиентов Т-Банка.
2. Объединить разрозненные данные о счетах, программах лояльности, выплатах и офферах в одном интерфейсе.
3. Реализовать backend без базы данных, используя только исходные CSV-файлы.
4. Реализовать интерактивный frontend без тяжелых frontend-фреймворков.
5. Обеспечить деплой frontend и backend на разных платформах.
6. Настроить автоматическую проверку и деплой через CI/CD.

## 3. Границы проекта

В рамках проекта реализуются:

- веб-интерфейс личного раздела лояльности;
- выбор клиента из тестового датасета;
- backend API для получения пользователей и персонального дашборда;
- расчет агрегированной аналитики по CSV;
- прогноз выгоды;
- достижения и прогресс;
- список партнерских предложений;
- рекомендации продуктов экосистемы;
- PWA-метаданные и иконки;
- деплой на Cloudflare Pages и Render;
- GitHub Actions workflow для тестов и деплоя.

В рамках проекта не реализуются:

- реальная авторизация через пароль, OAuth, SMS или биометрию;
- интеграция с реальными банковскими API;
- запись или изменение данных;
- платежные операции;
- административная панель;
- персональные данные реальных клиентов;
- серверная база данных.

## 4. Пользователи системы

### 4.1. Демонстрационный пользователь

Выбирает клиента из списка и просматривает персональный раздел лояльности.

### 4.2. Разработчик

Запускает проект локально, проверяет тесты, поддерживает код и CI/CD.

### 4.3. Проверяющий/жюри

Открывает готовый демо-сайт, проверяет сценарии, доступность backend и корректность расчетов.

## 5. Функциональные требования

### 5.1. Стартовый экран

Система должна:

- отображать список доступных клиентов из `Users.csv`;
- показывать количество клиентов, программ лояльности и партнеров;
- позволять искать клиента по имени или id;
- открывать личный раздел выбранного клиента без ввода пароля.

### 5.2. Личный дашборд

Система должна отображать:

- имя выбранного клиента;
- email и телефон клиента;
- суммарную выгоду по программам;
- количество активных счетов;
- прогноз выгоды;
- общий прогресс достижений.

### 5.3. Счета

Система должна:

- показывать все счета выбранного пользователя;
- отображать баланс счета;
- отображать программу лояльности счета;
- показывать сумму начислений по счету;
- раскрывать подробности счета по кнопке `Подробнее`;
- сворачивать подробности при повторном выборе.

### 5.4. Аналитика выплат

Система должна:

- строить график выплат по месяцам;
- показывать сумму выплат за период;
- показывать среднее значение выплат;
- выделять лучший месяц;
- раскрывать детализацию выплат по выбранному месяцу;
- сворачивать детализацию при повторном клике.

### 5.5. Прогноз

Система должна:

- рассчитывать прогноз выгоды на следующий месяц;
- рассчитывать прогноз на ближайшие 3 месяца;
- учитывать последние месяцы выплат и динамику активности.

### 5.6. Достижения

Система должна отображать 6 достижений:

1. Получать кешбэк несколько месяцев подряд.
2. Иметь активные счета.
3. Накопить кешбэк.
4. Хранить деньги на балансе.
5. Накопить максимум кешбэка за 1 месяц.
6. Совершать операции.

Для каждого достижения система должна показывать:

- название;
- описание;
- текущее значение;
- целевое значение;
- процент выполнения;
- признак выполнения.

Общий прогресс должен рассчитываться как среднее значение прогресса по всем достижениям.

### 5.7. Партнерские предложения

Система должна:

- читать партнеров из `Offers.csv`;
- отображать логотип, название, описание и процент кешбэка;
- учитывать доступность оффера по финансовому сегменту пользователя;
- показывать 8 доступных предложений до раскрытия;
- показывать полный список доступных предложений после нажатия `Показать все`.

### 5.8. Экосистема

Система должна:

- показывать 3 рекомендованных продукта Т-Банка;
- отображать название, описание, ссылку, детали и преимущества продукта;
- адаптировать рекомендации с учетом сегмента клиента и структуры выгоды.

### 5.9. AI-like insight

Система должна формировать текстовую рекомендацию на основе:

- наиболее выгодной категории/программы;
- доступных партнерских предложений;
- прогноза на следующий месяц;
- сегмента пользователя.

### 5.10. Тема интерфейса

Система должна:

- поддерживать темную и светлую темы;
- сохранять выбранную тему в `localStorage`;
- позволять переключать тему кнопкой в интерфейсе.

### 5.11. PWA

Система должна:

- иметь `manifest.json`;
- иметь иконки `192x192` и `512x512`;
- регистрировать service worker;
- отображать иконку на вкладке браузера;
- поддерживать standalone-режим установки приложения.

## 6. Backend API

Backend должен работать на Node.js и отдавать JSON API.

### 6.1. `GET /api/health`

Назначение: проверка состояния backend.

Ответ должен содержать:

- `ok`;
- список CSV-файлов;
- количество пользователей;
- количество офферов;
- количество программ лояльности.

### 6.2. `GET /api/users`

Назначение: получение списка клиентов для стартового экрана.

Ответ должен содержать список пользователей без внутренних сегментных полей.

### 6.3. `POST /api/login`

Назначение: поиск пользователя по email, телефону или id.

Тело запроса:

```json
{
  "login": "1"
}
```

Успешный ответ должен содержать:

- `userId`;
- `name`;
- `email`;
- `phone`.

При неизвестном пользователе API должен вернуть `401`.

При некорректном JSON API должен вернуть `400`.

### 6.4. `GET /api/users/:id/dashboard`

Назначение: получение полного персонального дашборда клиента.

Ответ должен содержать:

- данные пользователя;
- счета;
- сводные показатели;
- выплаты по месяцам;
- категории выплат;
- прогноз;
- офферы;
- продукты;
- достижения;
- AI-like insight.

Если пользователь не найден, API должен вернуть `404`.

## 7. Источники данных

Backend должен использовать только следующие CSV-файлы:

```text
data/Users.csv
data/Accounts.csv
data/LoyaltyPrograms.csv
data/Offers.csv
data/LoyaltyHistory.csv
```

Требования:

- CSV читаются при старте приложения;
- дополнительные CSV-файлы не используются;
- база данных не используется;
- данные доступны только для чтения;
- парсер CSV должен корректно обрабатывать BOM, кавычки и запятые внутри значений.

## 8. Нефункциональные требования

### 8.1. Производительность

- Стартовая страница должна загружаться как статический frontend.
- Backend должен отвечать на основные API-запросы без обращения к внешним сервисам.
- Расчеты выполняются в памяти на основе загруженного CSV-датасета.

### 8.2. Надежность

- Некорректный URL не должен ронять сервер.
- Некорректный JSON в login-запросе должен возвращать `400`.
- Неизвестный пользователь должен возвращать `404` для dashboard API.
- Непредвиденные ошибки должны возвращать JSON с сообщением об ошибке.

### 8.3. Безопасность

- Backend должен поддерживать CORS для Cloudflare Pages.
- `ALLOWED_ORIGINS` должен позволять ограничить список разрешенных frontend-доменов.
- API не должен отдавать внутренние поля сегментации на стартовый экран и в профиль пользователя.
- В проекте не должны храниться реальные персональные данные клиентов.

### 8.4. Совместимость

- Приложение должно работать в современных браузерах.
- Frontend должен корректно работать локально на same-origin API.
- Frontend должен корректно работать на Cloudflare Pages с внешним Render API.
- Backend должен запускаться локально и на Render.

### 8.5. Поддерживаемость

- Проект должен запускаться стандартными командами `npm ci`, `npm start`, `npm test`.
- README должен содержать актуальные ссылки, команды и описание деплоя.
- Техническое задание должно храниться в репозитории.

## 9. Требования к интерфейсу

Интерфейс должен:

- быть на русском языке;
- иметь адаптивную верстку;
- быть пригодным для демонстрации на desktop и mobile;
- использовать визуальную систему Т-Банка: желто-черную айдентику;
- не требовать регистрации;
- поддерживать hover-анимации карточек;
- не перекрывать текст и элементы управления на малых экранах.

## 10. Развертывание

### 10.1. Локальный запуск

```bash
npm ci
npm start
```

Локальный адрес:

```text
http://localhost:3000
```

### 10.2. Render backend

Backend разворачивается на Render как Web Service.

Настройки:

```text
Name: tbank-loyalty-hub-api
Runtime: Node
Build Command: npm ci
Start Command: npm start
Health Check Path: /api/health
```

Переменные окружения:

```text
NODE_ENV=production
ALLOWED_ORIGINS=https://tbank-loyalty-hub.pages.dev
```

Render URL:

```text
https://tbank-loyalty-hub-api.onrender.com
```

### 10.3. Cloudflare Pages frontend

Frontend разворачивается на Cloudflare Pages.

Настройки:

```text
Project name: tbank-loyalty-hub
Build command: npm run build:pages
Build output directory: public
```

Переменная окружения:

```text
API_BASE_URL=https://tbank-loyalty-hub-api.onrender.com
```

Cloudflare Pages URL:

```text
https://tbank-loyalty-hub.pages.dev/
```

## 11. CI/CD

CI/CD должен быть настроен через GitHub Actions.

Workflow: `.github/workflows/ci.yml`.

На pull request:

```text
npm ci
npm test
```

На push в `main`:

```text
npm ci
npm test
npm run build:pages
npx --yes wrangler@4 pages deploy public --project-name=tbank-loyalty-hub
```

GitHub Actions secrets:

```text
API_BASE_URL=https://tbank-loyalty-hub-api.onrender.com
CLOUDFLARE_ACCOUNT_ID=<Cloudflare Account ID>
CLOUDFLARE_API_TOKEN=<Cloudflare API token>
```

GitHub Actions variable:

```text
CLOUDFLARE_PAGES_PROJECT_NAME=tbank-loyalty-hub
```

Workflow должен проверять наличие обязательных secrets до запуска деплоя.

## 12. Тестирование

Тесты запускаются командой:

```bash
npm test
```

Тестовый набор должен проверять:

1. Наличие и загрузку 5 исходных CSV.
2. Количество пользователей.
3. Авторизацию по email и id.
4. Расчет персонального дашборда.
5. Расчет достижений и прогресса.
6. Health endpoint.
7. CORS-заголовки и preflight.
8. Список пользователей API.
9. Login API.
10. Dashboard API.
11. Обработку неизвестного пользователя.
12. Обработку некорректного URL.

Критерий успешного прохождения:

```text
All tests passed: 5 рабочих тестов
```

## 13. Критерии приемки

Проект считается принятым, если:

- frontend открывается по адресу `https://tbank-loyalty-hub.pages.dev/`;
- backend health check возвращает успешный JSON;
- пользователь может выбрать клиента и открыть личный раздел;
- отображаются счета, аналитика, прогноз, достижения, партнеры и продукты;
- кнопки раскрытия/сворачивания работают;
- тема переключается и сохраняется;
- API работает с Cloudflare Pages без CORS-ошибок;
- favicon отображается на вкладке сайта;
- PWA manifest доступен;
- `npm test` проходит локально и в GitHub Actions;
- push в `main` запускает CI/CD;
- Cloudflare Pages получает актуальный frontend после успешной сборки;
- Render backend запускается командой `npm start`.

## 15. Ограничения и допущения

- Проект является демонстрационным и использует тестовый CSV-датасет.
- Все расчеты выполняются на стороне backend в памяти.
- Данные не изменяются и не сохраняются после запуска.
- Авторизация упрощена до выбора/поиска клиента.
- Render free plan может переводить сервис в sleep-режим, поэтому первый API-запрос после простоя может быть медленнее.
- Cloudflare Pages отдает только статический frontend; API находится на Render.
